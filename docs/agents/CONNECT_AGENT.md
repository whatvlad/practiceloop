# Подключение второго ИИ-агента к PracticeLoop

Репозиторий: https://github.com/whatvlad/practiceloop (Private).
Подключение выполняется через Git и собственную GitHub-авторизацию человека,
под ответственностью которого работает агент. У ИИ не появляется доступ лишь
от знания ссылки. Другому человеку сначала нужен доступ к private-репозиторию;
его реальный GitHub username и приглашение согласуются с владельцем отдельно.
Не передавайте агенту токены в сообщении и не используйте общую папку двух агентов.

## До принятия инфраструктурного PR

Используйте отдельный клон. В main пока только оригинальная спецификация;
инфраструктура проходит review в chore/bootstrap-collaboration:
[PR #16](https://github.com/whatvlad/practiceloop/pull/16).

```powershell
git clone --branch chore/bootstrap-collaboration https://github.com/whatvlad/practiceloop.git practiceloop-agent
cd practiceloop-agent
git status --short --branch
git fetch origin --prune
```

В Claude Code откройте эту папку и выполните `claude`; в другом локальном агенте
откройте именно этот клон. Попросите сначала независимое review инфраструктурного
PR по тексту ниже. Не редактируйте ветку реализации Codex напрямую.

## Готовое сообщение агенту

Ты подключаешься к private-репозиторию https://github.com/whatvlad/practiceloop.
Работай в собственном clone/worktree под GitHub-аккаунтом своего человека-владельца.
Не проси отправить токены в чат; используй штатную авторизацию Git/GitHub.

1. Проверь текущую ветку, Git status и remote; безопасно получи актуальные изменения.
2. Прочитай AGENTS.md, CLAUDE.md (если ты Claude Code), исходную спецификацию
   docs/PRACTICELOOP_MVP.md, docs/agents/STATUS.md, WORKFLOW.md, TASK_PROTOCOL.md,
   REVIEW_PROTOCOL.md, HANDOFF.md и релевантные ADR.
3. Проверь открытые Issues и PR. Сначала открой PR #16 из chore/bootstrap-collaboration
   в main и проведи независимое review реального diff. Обозначь свою настоящую
   идентичность агента, человека-владельца, проверенный commit и запущенные проверки.
4. Не выдавай ИИ-review за человеческое одобрение. Не выполняй merge, не меняй
   доступы и не переписывай чужую ветку. Замечания дай с severity/file/line,
   последствиями и предложением исправления. Передай результат своему человеку.
5. После принятия инфраструктурного PR человеком выбери с владельцем одну
   свободную Issue с выполненными зависимостями. До этого не начинай реализацию MVP.
6. Зафиксируй владельца и scope, создай свою ветку от актуального main вида
   feature/issue-N-short-description. Не работай напрямую в main и не меняй
   одновременно те же файлы, что другой агент.
7. Реализуй только критерии Issue. Запусти реальные проверки из README, проверь
   diff и секреты, обнови документацию. Публикуй свою рабочую ветку и PR только
   в пределах разрешения своего человека; merge требует отдельного разрешения.
8. В конце дай HANDOFF: агент/владелец, Issue/PR, ветка/commit, scope, результаты
   проверок, ограничения, открытые замечания и следующий шаг.

Начальное предложение: Codex + Developer 1 — frontend/KaTeX/сценарии;
Claude Code + Developer 2 — FastAPI/SymPy/Supabase. Это не фактическое назначение.
Сначала согласуйте общие API и открытые решения, не начинайте все функции сразу.

## После merge инфраструктурного PR

Только при чистом рабочем дереве:
```powershell
git fetch origin --prune
git switch main
git pull --ff-only
```
При первом клонировании сразу ветки review локальной main может ещё не быть;
`git switch --track origin/main` создаст её. Перед feature-веткой подставьте
реальный номер согласованной свободной Issue, не копируйте выдуманный номер.
GitHub — источник принятого кода и задач; локальные Markdown-файлы не создают
автоматической синхронизации между компьютерами или агентами.
